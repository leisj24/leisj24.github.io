### 第1章：计算机网络和因特网

#### 1.1 因特网、Web、端系统、接入网、网络核心

**因特网是由多个独立网络互连形成的网络的网络。** ISP之间存在客户—提供商关系和对等互连关系，形成一定的层次结构，但不存在统一的行政控制关系，也不具有严格的树形层次。

从具体构成看，因特网由端系统、通信链路和交换设备组成；从服务角度看，因特网是为分布式应用提供通信服务的基础设施。Web、电子邮件和文件传输均为运行在因特网上的应用，**Web与因特网属于不同概念**。

| 名称 | 定义 | 主要作用 |
|---|---|---|
| 端系统 / 主机 | 运行网络应用程序的设备 | 产生和接收数据，运行应用层与传输层协议 |
| 接入网 | 连接端系统与边缘路由器的网络 | 为用户和机构提供网络接入 |
| 网络核心 | 由路由器及互连通信链路组成的网状网络 | 在网络边缘之间转发分组 |
| 本地 / 接入 ISP | 直接向用户提供上网服务的运营网络 | 接入用户和机构网络 |
| 地区 ISP | 汇集一个地区的多个接入网络 | 区域互连并连接更大网络 |
| 第一层 ISP | 覆盖范围很广的骨干网络 | 与其他骨干对等互连，提供广域可达性 |
| IXP | 多个网络进行对等互连和流量交换的场所 | 支持ISP对等互连 |
| PoP | 运营商向客户网络提供接入的一处存在点 | 连接客户网络与运营商网络 |
| 多宿 multi-home | 同时接入多个上游 | 增加可达性和冗余，减少单一上游依赖 |

**选路与转发：** 选路决定分组从源主机到目的主机所经过的路径；转发指路由器根据转发表，将到达的分组从输入接口送至相应输出接口。选路涉及网络范围内的路径计算，转发是节点执行的本地操作。

#### 1.2 接入技术和物理媒体

| 技术 | 主要媒体 | 主要特点 |
|---|---|---|
| DSL | 电话双绞线 | 电话与数据使用不同频带；用户至局端的线路独立，速率受传输距离影响 |
| HFC / 有线电视接入 | 光纤 + 同轴电缆 | 同一接入段用户共享容量；上、下行可以使用不同频带 |
| 以太网 | 双绞线、光纤 | 常见于校园和企业局域网 |
| Wi-Fi | 无线电波 | 通过无线接入点连接局域网；无线信道共享 |
| 蜂窝接入 | 无线电波 | 通过基站和移动运营商网络接入，覆盖范围较广 |
| 光纤接入 | 光纤 | 容量高、抗电磁干扰，适合长距离和骨干通信 |

物理媒体分成导引型和非导引型：双绞线、同轴、光纤属于前者；无线电波属于后者。

**链路传输速率R（bit/s）与信号传播速度s（m/s）应分别考虑。** 前者表示单位时间内发送到链路上的比特数，后者表示信号在媒体中的传播速度。提高链路传输速率可以降低传输延迟，但不改变给定媒体中的传播速度。

#### 1.3 分组交换和电路交换

**电路交换：** 在通信开始前建立端到端电路并预留资源，通信期间各链路上的相关资源由该连接占用。即使用户暂时不发送数据，预留资源也不能供其他连接使用。传统电话网络是典型的电路交换网络。

**分组交换：** 发送方将报文划分为分组，分组按需共享网络链路与交换设备资源。分组交换适合突发流量，资源利用率较高，但可能产生排队、丢包和拥塞。

| 比较点 | 电路交换 | 分组交换 |
|---|---|---|
| 通信前 | 建立电路、预留资源 | 无需先预留端到端电路 |
| 资源分配 | 会话期间固定占用 | 按需共享，统计复用 |
| 空闲期间 | 已预留资源可能浪费 | 其他用户可以使用资源 |
| 负载很高时 | 可能拒绝建立新电路 | 可能排队、丢包、拥塞 |
| 性能 | 已建立电路有较稳定的容量 | 延迟和可用吞吐量随负载变化 |

**因特网采用分组交换的原因：** 文件传输和电子邮件等应用具有突发通信特征，固定预留资源会造成空闲期间的容量浪费。统计复用使多个用户共享链路容量，并允许轻负载时的活跃用户使用更多可用带宽。相应地，网络需要通过可靠传输和拥塞控制机制处理丢包、乱序及负载变化。

分组交换可以承载音视频应用，但尽力而为服务本身不提供严格的带宽和时延保证。应用可采用播放缓存、自适应编码等机制适应网络条件。

**FDM与TDM：** 频分复用将链路频带划分为多个子频带，各电路持续占用相应频带；同步时分复用将时间划分为重复的帧，各电路固定分配若干时隙。分组交换采用按需的统计复用，其链路使用模式不是预先固定的。

**链路与电路：** 链路是设备间的通信通道；电路是为一次通信预留的逻辑资源，一条链路可以承载多条电路。

#### 1.4 存储转发与流水线传输

课程采用存储转发模型：路由器接收完整分组后，才能将其发送到下一条链路。该模型便于进行分组处理和差错检测；实际交换设备也可能采用其他转发方式，计算题应以题设模型为准。

一个长度 L bit 的分组，经过 N 条速率都为 R bit/s 的链路，忽略其他延迟：

`T_单分组 = N × L/R`

P 个等长分组连续发送时：

`T_全部 = (N + P - 1) × L/R`

第一个分组需要完成N次链路传输。流水线建立后，不同链路可以同时传输不同分组，因此目的端每隔L/R接收一个后续分组。

**例：** 分组经过3条链路，每次链路传输时间为2ms，共100个等长分组。第一个分组在6ms到达，最后一个分组的到达时间为`6+99×2=204ms`。计算`100×3×2=600ms`未考虑不同链路的并行传输。

各跳存在固定传播延迟时，应在总时间中加入相应传播延迟之和。上述公式假设链路速率相同、分组等长、连续发送且无拥塞，并忽略影响流水线传输间隔的处理瓶颈。

更一般地，忽略传播和处理，对等长分组、不同速率的串行链路，连续无阻塞流水线传输可写为：

`T = Σ(L/R_i) + (P-1) × max(L/R_i)`

第一个分组的传输时间由各链路传输延迟之和决定，后续分组的到达间隔由瓶颈链路决定。若题目涉及排队、可变分组长度或其他调度约束，应通过时间线分析确定完成时间。

#### 1.5 分组延迟及其组成

| 延迟 | 定义 | 公式 / 主要影响因素 |
|---|---|---|
| 处理延迟 | 检查分组首部、检测差错并确定输出链路所需时间 | 设备处理能力和处理任务 |
| 排队延迟 | 分组在输出缓存中等待链路传输的时间 | 链路负载、流量突发性、队列长度 |
| 传输 / 序列化延迟 | 将分组的全部比特发送到链路上所需时间 | `L/R` |
| 传播延迟 | 信号从链路一端传播到另一端所需时间 | `d/s` |

`d_节点 = d_处理 + d_排队 + d_传输 + d_传播`

**传输过程与传播过程可以重叠。** 首个比特开始传播时，发送方可能仍在发送后续比特。以最后一个比特到达接收端为完成时刻，空闲链路上的分组延迟为`L/R+d/s`。

**例：** 1500 B 的包，10 Mbps 链路，距离 1000 km，传播速度 `2×10^8 m/s`。

- L = 1500×8 = 12000 bit。
- 传输延迟 = 12000 / 10^7 = 1.2 ms。
- 传播延迟 = 10^6 / (2×10^8) = 5 ms。
- 忽略处理与排队，最后一个比特在 6.2 ms 到达。

**各类延迟的相对大小取决于具体条件。** 卫星链路可能以传播延迟为主，低速链路传输长分组时可能以传输延迟为主，重负载路由器可能以排队延迟为主。2019年选择题考查了这一结论。

**延迟抖动：** 在路径、分组长度和链路速率固定时，传输延迟与传播延迟相对稳定，抖动主要来自输出队列积压程度的变化。分组长度、路径或处理负载变化时，其他延迟分量也可能产生波动。

#### 1.6 排队、流量强度、丢包

设平均分组到达率为a个/s，分组长度为Lbit，输出链路速率为Rbit/s：

`ρ = aL/R`

流量强度表示平均输入数据速率与链路服务能力之比。ρ较小时平均排队延迟通常较小；ρ接近1时延迟明显增大；ρ长期大于1时输入速率超过输出能力，无限缓存系统不能达到稳定状态。

**平均到达率低于服务能力并不排除排队。** 分组到达具有突发性，短时间内的到达量可能超过链路在该时段内的传输能力。

无限缓存模型可能出现无界增长的队列长度与延迟；实际有限缓存达到容量上限后会发生丢包。两者基于不同的缓存假设，应分别分析。

**一批分组同时到达：** 空队列同时收到 N 个等长包，按先来先服务，排队时间依次为 `0, L/R, 2L/R, …, (N-1)L/R`，所以：

`平均排队时间 = (N-1)L/(2R)`

上述结果仅包含排队时间。若求分组从到达到完成传输的平均时间，还应加上自身的传输延迟L/R。

**缓存容量的取舍：** 较小缓存更容易因突发到达而溢出；较大缓存可能增大排队延迟，降低交互应用的响应性能，并引发发送端超时。缓存容量应综合延迟和丢包要求确定。

#### 1.7 带宽、吞吐量、瓶颈和带宽时延积

**链路带宽与吞吐量：** 链路传输速率描述单位时间内可传输的数据量，吞吐量描述单位时间内实际成功交付的数据量。吞吐量可分为瞬时值与平均值，分析时还应区分链路总数据速率与应用有效数据速率。

对经过多条串行链路的单条数据流，在无其他流量且忽略协议限制时：

`端到端吞吐量 ≈ min(R_1, R_2, …)`

若 N 条连接公平共享速率 R 的中间链路：

`每条连接吞吐量 ≈ min(R_服务器, R_客户, R/N)`

大文件传输时间可近似为`F/吞吐量`。若要求精确完成时间，还应考虑连接建立、首个分组的端到端延迟以及末尾分组的传播时间。

**带宽时延积：**

`BDP_单向链路 = R × d_传播`

带宽时延积表示连续发送状态下，链路能够同时承载的在途比特量。以R=5Mbps、单向传播延迟80ms为例，BDP=400000bit。

滑动窗口分析常采用**R×RTT**估计等待反馈期间所需维持的在途数据量。单向链路BDP与基于RTT的发送窗口估算采用不同的时延定义。

单个比特在链路上的空间长度为`宽度=s/R`。传播速度固定时，传输速率越大，单个比特对应的空间长度越小。

#### 1.8 协议、服务、接口、分层、封装

网络协议定义通信实体之间交换的**报文格式、交换次序，以及发送或接收报文和发生其他事件时采取的动作**。协议分析应同时说明这三类要素。

| 概念 | 定义 |
|---|---|
| 协议 | 不同系统中对等层实体进行通信时遵循的规则 |
| 服务 | 某一层向其上层提供的功能 |
| 接口 | 相邻层之间调用服务和交换信息的方式 |

**协议描述对等层实体间的通信，服务与接口描述相邻层之间的关系。** 浏览器和Web服务器使用HTTP协议，应用通过socket接口调用传输层服务。报文首部承载供对等层解释的控制信息，相邻层通过接口使用服务。

| 五层，从上到下 | 主要工作 | 数据名称 | 典型例子 |
|---|---|---|---|
| 应用层 | 定义具体应用双方如何交换信息 | 报文 message | HTTP、DNS、SMTP |
| 传输层 | 进程到进程通信 | 报文段 segment / UDP 数据报 | TCP、UDP |
| 网络层 | 主机到主机、跨网络交付 | IP 数据报 / 分组 | IP |
| 链路层 | 相邻节点之间传递帧 | 帧 frame | 以太网、Wi-Fi |
| 物理层 | 在媒体上传输信号和比特 | 比特 bit | 电、光、无线信号 |

OSI 七层在应用和传输之间增加表示层、会话层。因特网五层模型把需要的这类功能放到应用等相关部分实现。

封装过程中，应用报文依次增加传输层首部、网络层首部以及链路层首部和尾部；接收端按相反顺序解封装。某层将来自上层的协议数据单元作为载荷。

**主机处理完整五层协议栈；路由器的典型转发功能涉及底三层；二层交换机的转发功能涉及底两层。** 路由器可能另行运行管理应用，设备层次题通常针对数据转发路径进行讨论。

分层的好处是模块化、便于更新和定位问题；代价是层间可能重复某些功能，严格分层也可能限制优化。应用不必知道中间每个路由器如何实现。

#### 1.9 网络安全与因特网发展

- 恶意软件：病毒通常依附其他程序传播；蠕虫可自行复制传播。
- DoS / DDoS：耗尽目标服务或网络资源，使正常用户无法使用；DDoS 是多个来源协同攻击。
- 嗅探：被动观察经过的数据；伪装：冒充源地址或身份；重放：把以前有效的信息再发一次。
- 僵尸网络：由多个受攻击者控制的设备组成，可被协同用于实施攻击。
- 早期因特网侧重互联与通信，安全不是默认完备的属性；详细密码学不在本次第 1–3 章讲义展开。
- 发展主线：分组交换思想 → ARPANET → TCP/IP互联 → Web普及 → 移动互联网、云计算和物联网。课件中的设备数量和部署规模属于历史示例，应结合相应年份理解。

应掌握分组交换对突发流量的适应性，传输延迟与传播延迟的定义及计算，存储转发流水线的完成时间，排队产生的条件，以及协议、服务、接口和各类设备的协议层次。

### 第2章：应用层

#### 2.1 网络应用、进程、客户和服务器

网络应用由运行在不同端系统上的进程组成，通过交换报文完成协作。网络核心设备负责数据转发，通常不参与应用层的业务处理。

**进程是正在运行的程序。** 本机的进程可以用操作系统提供的本地通信机制；不同主机的进程通过网络交换信息。

一次通信中，主动发起联系的进程为客户进程，等待联系并提供服务的进程为服务器进程。P2P对等方可以在不同交互中同时承担两种角色，例如下载时请求资源、上传时提供资源。**P2P架构不具有固定中心服务器，但具体交互仍可区分客户和服务器角色。**

| 架构 | 核心特点 | 优点 | 主要代价 |
|---|---|---|---|
| C/S | 资源主要由固定服务器提供，服务器通常持续可用 | 便于管理和维护 | 服务器、出口带宽、运维可能成为瓶颈 |
| P2P | 对等方既消费又提供资源 | 新用户也带来服务能力，具有自扩展性 | 节点上下线、地址变化、安全和管理更复杂 |

C/S架构的服务器可由多台主机或多个数据中心构成。C/S与P2P的本质区别在于资源提供角色是否主要集中于固定的服务器端，而非服务器的物理台数。

#### 2.2 套接字与进程寻址

应用进程通过套接字（socket）发送和接收数据。套接字是应用层与传输层之间的接口，应用通过该接口使用传输服务。

标识远程通信端点需要**IP地址和端口号**：IP地址标识主机的网络接口，端口号用于传输层解复用。端口号为16bit，取值范围0–65535，其中0–1023为熟知端口范围；同一进程可以使用多个套接字。

**监听套接字与连接套接字：** TCP服务器首先创建监听套接字；接收连接请求后，`accept()`返回与该客户通信的连接套接字。监听套接字继续接收其他连接请求。

典型TCP服务器同时维护n条客户连接时，服务端需要**1个监听套接字和n个连接套接字**。各连接可使用相同的服务器端口，通过连接四元组进行区分，详见第三章。

课件以创建新进程处理客户连接为例。服务器也可采用线程或事件循环实现并发服务，每条TCP连接需要独立的连接状态，但不必对应一个独立进程。

#### 2.3 应用对传输服务的需求及TCP/UDP服务

应用对传输服务的需求主要包括数据完整性、吞吐量、时延和安全性。文件传输要求数据完整；语音通信可容忍少量丢失，但对延迟较敏感；视频点播可通过播放缓存适应短时吞吐量变化。

| 服务 | TCP | UDP |
|---|---|---|
| 建立连接 | 需要 | 不需要 |
| 可靠、有序 | 提供可靠有序字节流 | 本身不保证交付和顺序 |
| 消息边界 | 不保留应用消息边界 | 保留数据报边界 |
| 流量控制 | 有 | 本身没有 |
| 拥塞控制 | 有 | 本身没有 |
| 固定带宽、固定时延承诺 | 没有 | 没有 |
| 自动加密 | 基础 TCP 没有 | 基础 UDP 没有 |

**UDP减少了连接建立和传输控制带来的等待，但不提供交付时间或低延迟保证。** 应用可在UDP之上实现可靠传输与拥塞控制，QUIC属于这一类协议。

#### 2.4 Web对象与HTTP基本原理

网页通常包含一个基础HTML文件及其引用的图片、CSS和脚本等对象。浏览器获取并解析HTML后，确定后续需要请求的对象。**一个HTML文件和n张图片通常对应n+1个对象及n+1次HTTP请求。**

URL包含访问协议、服务器主机名和资源路径，例如`http://example.com/a/p.jpg`。DNS解析其中的主机名`example.com`，不解析完整URL或资源路径`/a/p.jpg`。

HTTP 采用请求/响应交互。按课程的 HTTP/1.x 模型使用 TCP，默认 HTTP 服务端口 80；HTTPS 常用 443。HTTP/3 的传输另见后文。

**无状态性：** 基础HTTP协议不要求服务器保存客户先前请求的状态。应用仍可通过Cookie、服务器数据库及会话机制实现用户身份关联和状态管理。

#### 2.5 三种 HTTP 连接方式和时间计算

设客户端至源服务器的RTT为T，DNS查询总时间为D。忽略请求报文、首部及小对象的传输时间，假设所有对象位于同一服务器且DNS查询串行执行。

在一条新建立的TCP连接上获取一个小对象，教材的基本RTT模型为：

`1 RTT建立TCP连接 + 1 RTT完成请求/响应 = 2T`

| 连接方式 | 工作过程 | HTML+n个小对象的总时间 |
|---|---|---|
| 非持久、无并行 | 每个对象使用独立TCP连接 | `D + 2(n+1)T` |
| 持久、无流水线 | 复用TCP连接，收到前一响应后发送下一请求 | `D + (n+2)T` |
| 持久、流水线 | 获取HTML后，连续发送各对象请求 | `D + 3T`，n≥1 |
| 非持久、最多k条并行连接 | 先获取HTML，再分批并行获取引用对象 | `D + 2T + 2ceil(n/k)T` |

n=0时仅请求HTML文件，总时间为D+2T，不包含引用对象的请求阶段。

**例：** 网页引用8个小对象，浏览器允许6条并行连接。获取HTML需要2T，引用对象分两批获取，每批需要2T，因此总时间为D+6T。

对象较大时，应计入传输时间。设n张图片的长度均为Lbit，所有连接共享速率为R的瓶颈链路：

- 串行非持久：`2(n+1)T + nL/R`（HTML 长度忽略）。
- 持久无流水线：`(n+2)T + nL/R`。
- 流水线持久：`3T + nL/R`。
- 使用n条并行非持久连接获取图片：简化模型下为`4T + nL/R`。

并行连接共享同一瓶颈时，总数据量nLbit仍需要nL/R的传输时间。若题目明确每条连接具有独立的速率R，图片传输阶段才可按L/R计算。

上述公式采用教材的理想化RTT模型，未计入TCP慢启动、丢包恢复、TLS握手或阶段重叠。涉及这些因素时，应依据题设补充相应时间。

**耗时分析顺序：** DNS解析 → TCP连接建立 → HTML请求与接收 → HTML解析 → 引用对象请求 → 对象数据传输。各阶段的成本应按依赖关系及并行条件计算。

#### 2.6 HTTP报文格式与字段功能

```text
GET /index.html HTTP/1.1
Host: example.com
Connection: keep-alive
If-Modified-Since: ...
空行
可能的报文体
```

请求行由方法、路径、版本组成；后面是首部行；空行分开首部和报文体。普通 GET 通常没有请求体。

```text
HTTP/1.1 200 OK
Date: ...
Last-Modified: ...
Content-Type: text/html
Content-Length: ...
空行
HTML 内容
```

| 字段 / 方法 | 含义 |
|---|---|
| GET | 请求资源 |
| HEAD | 请求类似 GET 的响应首部，不返回资源内容 |
| POST | 向服务器提交数据，请求体常携带表单等 |
| PUT / DELETE | 创建或替换指定资源 / 删除指定资源 |
| Host | 标识请求的主机，支持同 IP 上不同站点 |
| Content-Type | 内容类型，如 HTML、JPEG |
| Content-Length | 内容长度，不是整个 TCP 段的长度 |
| Date | 响应生成的时间 |
| Last-Modified | 资源最后修改的时间 |

Date表示响应生成时间，Last-Modified表示对象最后修改时间。**HTTP报文边界与TCP报文段边界不一致：** 一个HTTP报文可由多个TCP段传输，一个TCP段也可携带相邻应用报文的字节。

常见状态码：200 成功；301 永久重定向；304 缓存资源未修改，响应不带该资源内容；400 请求有误；401 需要认证；404 找不到；505 不支持请求中使用的 HTTP 版本。

#### 2.7 Cookie、Web缓存与条件GET

**Cookie用于关联用户身份及请求状态。** 课程模型包括四个组成部分：响应报文中的`Set-Cookie`首部、后续请求中的`Cookie`首部、浏览器保存的Cookie及服务器后台记录。Cookie可辅助实现购物车、登录状态和个性化服务，也涉及行为跟踪与隐私问题。

**Web缓存用于保存和提供资源副本。** 缓存对浏览器充当服务器，对源服务器充当客户。缓存命中时直接返回对象，未命中时从源服务器获取对象并保存副本。其主要作用是降低响应时间、减轻源服务器负载并减少机构出口流量。

**条件GET用于验证缓存副本的有效性。** 缓存使用`If-Modified-Since`或基于ETag的条件请求；对象未修改时源服务器返回304，已修改时返回更新后的对象。

缓存耗时分析应区分以下条件：

- 缓存副本可直接使用时，若忽略局域网传输成本，命中时间可近似为0。
- 要求向源服务器验证时，即使返回304，也需要一次远端请求/响应往返。
- 验证所用TCP连接尚未建立时，应计入握手时间；对象串行验证时，应计入多次往返。

**缓存命中并不必然意味着响应时间为0。** 是否需要源服务器验证、连接是否已经建立及请求调度方式共同决定时间成本。2024年简答第3题涉及这些条件。

缓存与排队结合的计算，若接入链路速率 R，平均对象长度 L，到达率 a，命中率 h：

`Δ = L/R`，`a_出口 = (1-h)a`，`ρ_出口 = a_出口Δ`

题目给排队模型时，未命中的接入平均时间可用 `Δ/(1-ρ_出口)`，但**仅在 ρ_出口<1 的稳定模型中适用**。

`总平均响应时间 = h×T_命中 + (1-h)×T_未命中`

计算时应区分命中率h与未命中率1-h。缓存降低的是出口请求率，未命中对象的长度仍按原对象长度计算。

#### 2.8 HTTP及相关Web机制的演化

| 机制 | 设计背景 | 主要方法 |
|---|---|---|
| 持久连接 | 每个对象都重建 TCP，重复握手 | 重用同一连接 |
| Cookie | 请求之间缺少用户状态关联 | 携带标识并关联会话 |
| Web 缓存 | 远端响应慢、源站和出口压力大 | 就近保存副本 |
| 条件 GET | 副本可能过期 | 回源验证，未改时不用重传内容 |
| HTTP/2 | HTTP/1.1 有对象响应顺序造成的阻塞 | 帧化并交错发送多个流 |
| HTTP/3 | TCP 的统一有序字节流在丢包时影响多个应用流 | 使用 QUIC 的多流传输 |

**HTTP/2通过多流帧交错缓解应用层队头阻塞，但TCP丢失报文段仍可能阻塞同一连接后续字节的交付。** HTTP/3基于QUIC，各流可独立有序交付，因此一个流的数据缺失不必阻塞其他流；连接级拥塞控制仍会对发送行为产生影响。[HTTP/3标准说明](https://www.rfc-editor.org/rfc/rfc9114.html)

课件介绍HTTP/2的优先级和服务器推送机制，用于说明其设计方法。具体支持情况与实现有关，应区分协议机制和浏览器行为。

#### 2.9 电子邮件系统、邮件传输与访问

典型邮件传递路径如下：

```text
Alice 用户代理
   → Alice 邮件服务器的发送队列
   → Bob 邮件服务器的用户信箱
   → Bob 用户代理
```

电子邮件交付包括两个阶段：首先投递至收件人邮件服务器上的永久信箱，再由用户代理访问该信箱。邮件服务器持续在线，用户终端可能间歇接入，因此永久信箱通常使用服务器的持久存储。

| 协议 | 使用场景 | 课程端口 | 主要特点 |
|---|---|---|---|
| SMTP | 用户代理提交邮件、服务器之间投递邮件 | TCP 25（课程基本模型） | 推送、命令/响应、可复用连接传多封邮件 |
| POP3 | 用户代理访问邮箱 | TCP 110；加密访问常用 995 | 下载取信，可配置保留或删除服务器副本 |
| IMAP | 用户代理访问邮箱 | TCP 143；加密访问常用 993 | 邮件主要在服务器管理，便于多设备和文件夹同步 |
| HTTP / HTTPS | 浏览器使用 Webmail | 80 / 443 | 浏览器提交、读取邮件；后台跨邮件服务器仍用 SMTP |

**SMTP用于邮件提交和投递，不用于用户代理读取已有邮箱内容。** 邮件访问可使用POP3、IMAP或基于HTTP的Webmail。

**SMTP典型交互：** 服务器就绪 → HELO/EHLO → MAIL FROM → RCPT TO → DATA → 邮件内容 → 单独一行句点结束内容 → QUIT。SMTP信封地址与邮件内容中的From/To首部具有不同的语义。

课程基本模型里发送方邮件服务器可直接联系收件方邮件服务器；实际也可以有中继服务器。因此“服务器之间逐跳转交”可描述邮件中继，**不意味着每台 IP 路由器都在运行 SMTP**。

**MIME的作用：** 原始SMTP以7bit ASCII文本为基础，不能直接表示任意二进制内容。MIME扩展内容类型和传输编码，使非ASCII文本及二进制内容能够经编码后传输。

- `Content-Type`：表示内容类型，例如`image/jpeg`。
- `Content-Transfer-Encoding`：表示传输编码方式，例如`base64`。
- Base64：3 个字节共 24 bit，切成四组 6 bit，各映射成一个 ASCII 字符；不足补 `=`。编码后长度约增至原来的 4/3，精确为 `4ceil(n/3)` 字符，不算换行。
- quoted-printable：适合主要是 ASCII 的文本，需编码的字节可表示成 `=HH`。

Base64 是编码，**不是加密**。

#### 2.10 DNS：域名系统

DNS是保存资源记录的分布式数据库及相应的应用层查询协议，提供主机名到地址的映射、主机别名、邮件服务器查询及负载分配等服务。

**采用分布式结构的原因：** 集中式DNS存在单点故障、查询流量集中、远距离访问延迟较大及数据库维护规模过大等问题。

主机地址和名字不是一一对应：一台服务器可以有多个名字，一个名字可以返回多个地址，不是每台因特网主机都必须注册域名。

##### 名字树与 DNS 服务器层次

`www.example.com.` 从右往左是根 `.`、顶级域 `com`、下一级域 `example`、标记 `www`。名字层次帮助分级管理，不是地理位置或 IP 路由的层次。

| DNS角色 | 职责 |
|---|---|
| 根DNS | 提供顶级域服务器的地址信息 |
| TLD DNS | 提供相应域的权威服务器信息 |
| 权威DNS | 保存并回答其负责区域的资源记录 |
| 本地DNS | 代理用户查询，使用缓存并联系其他DNS服务器 |
| 主机解析器 | 应用调用的本地组件，向本地DNS提交查询并返回结果 |

**本地DNS不属于根、TLD和权威服务器的层次结构。** 课程中的主机解析器通常指stub resolver，主要查询工作由本地DNS完成。其他资料也可能使用resolver指递归DNS服务器，应结合语境区分。

DNS 的域 domain 与区域 zone 不完全相同：域是名字树的一棵子树；zone 是一套权威管理范围，委派出去的子域由另外的 zone 管理。逻辑名字树的层次不必与物理服务器台数一一对应。

根服务具有13个逻辑标识，每个标识可对应多个物理服务实例。课件中的部署图属于DNS层次结构的历史示例。

##### 递归、迭代、缓存

**递归查询：** 接收查询的服务器负责继续完成名称解析，并向请求方返回最终结果。

**迭代查询：** 接收查询的服务器返回已知答案或后续服务器信息，由请求方继续发起查询。

典型过程为应用调用主机解析器，解析器向本地DNS提交递归查询；本地DNS依次向根、TLD和权威服务器进行迭代查询，再返回结果。已有缓存可以减少查询层次，或直接满足请求。

```text
主机 → 本地DNS：请求解析www.example.com
本地DNS → 根DNS：查询com顶级域服务器信息
本地DNS → com TLD：查询example.com权威服务器信息
本地DNS → 权威DNS：查询www.example.com地址记录
本地DNS → 主机：返回解析结果
```

该过程包括4个请求和4个响应，其中**本地DNS发出的外部查询为3个**。查询数、请求与响应总数以及特定节点发送的查询数采用不同计数范围。

DNS缓存记录受TTL约束。已缓存Web地址记录并不代表已缓存MX记录，但先前查询可能同时缓存权威服务器信息，从而使后续查询跳过根和TLD服务器。

##### DNS资源记录

记录包含 name、type、value、TTL；列顺序依题目而定。

| 类型 | name | value | 映射关系 |
|---|---|---|---|
| A | 主机名 | IPv4 地址 | 名字 → 地址 |
| AAAA | 主机名 | IPv6 地址 | IPv6 版地址记录 |
| NS | 域名 | 权威服务器名字 | 域名 → 权威服务器 |
| CNAME | 别名 | 规范名字 | 别名 → 规范名 |
| MX | 邮件域 | 邮件服务器名字，另有优先级 | 邮件域 → 邮件服务器 |
| PTR | 反向地址名字 | 主机名 | 地址 → 名字 |

例：Web和FTP服务由`star.example.com`提供，邮件服务由`moon.example.com`提供，相应资源记录为：

```text
www.example.com     CNAME  star.example.com
ftp.example.com     CNAME  star.example.com
star.example.com    A      212.212.212.3
example.com         MX     moon.example.com
moon.example.com    A      212.212.212.4
```

MX和NS记录的value通常为主机名，需要结合A/AAAA记录获取地址。父域委派提供NS记录，并在必要时附加glue地址记录，以解决查询权威服务器地址时的循环依赖。

IPv4 反向例：`132.34.45.121` 可对应查询 `121.45.34.132.in-addr.arpa` 的 PTR。

##### DNS 报文与传输

查询和响应使用同一种基本格式：首部、问题、回答、权威、附加四个数据区。首部含事务 ID、查询/响应标志、递归期望/可用、权威回答、截断标志，以及各区记录数。附加区可提供下一步需要的地址，减少后续查询。

DNS 常用 UDP 53，也可用 TCP 53。小查询用 UDP 可免去建连成本，失败时应用可重试。**请求不总是 UDP，响应也不总是 UDP。**

课件采用传统DNS的512B UDP报文限制模型：响应截断时TC=1，客户可通过TCP重试。EDNS允许协商更大的UDP载荷，因此512B限制不能直接推广为现代DNS的统一传输规则。[EDNS标准说明](https://www.rfc-editor.org/rfc/rfc6891.html)

DNS安全问题包括缓存投毒、查询劫持和服务不可用。缓存投毒通过伪造响应污染缓存记录；查询劫持通过改写或拦截查询影响解析；DNS服务故障会影响依赖域名解析的应用。

#### 2.11 P2P 文件分发与 BitTorrent

F bit 的文件发给 N 个客户，服务器上传速率 u_s，第 i 个客户上传速率 u_i，最慢下载速率 d_min：

`D_CS ≥ max(NF/u_s, F/d_min)`

服务器需要上传N份文件，因此分发时间至少为NF/u_s；下载能力最弱的客户接收完整文件至少需要F/d_min。

`D_P2P ≥ max(F/u_s, F/d_min, NF/(u_s+Σu_i))`

服务器至少需要向系统注入一份完整文件，耗时不小于F/u_s；最慢客户的下载时间不小于F/d_min；所有客户总共接收NFbit，系统总上传能力为u_s+Σu_i。上述表达式是理想模型下的分发时间下界，其可达性取决于调度和其他网络约束。

P2P 自扩展：新用户带来下载需求，也带来上传容量。

BitTorrent采用分块文件传输。tracker维护对等方信息，用于发现可连接的节点；稀缺块优先策略提高块的可用性；对等方优先向提供较好上传服务的节点发送数据，并通过试探性解除阻塞发现新的合作节点。

课件还比较目录发现：集中式目录容易管理但存在瓶颈；查询泛洪分散但消息多；层次覆盖网络由部分节点充当超级节点，折中两者。资源发现方式与实际数据传输架构要区分：有中心目录不代表所有文件必须通过目录服务器转发。

#### 2.12 视频、DASH 和 CDN

视频播放以一定速率持续消耗数据。平均接收速率长期低于播放码率时，播放缓存最终耗尽；短时速率变化可由缓存平滑。

CBR 是恒定码率，VBR 的码率随内容变化。压缩可利用空间相似性和相邻帧的时间相似性。

**DASH：** 服务器将视频划分为多个块，并为各块提供不同码率的版本；清单文件给出对应URL。客户端依据可用带宽及缓存状态逐块选择适当版本，实现动态自适应流式传输。

**CDN：** 在多个地理分布站点部署内容副本，并将用户请求导向网络条件较好的节点，以缓解集中式服务器瓶颈并降低访问延迟。enter deep将大量节点深入部署至接入网络；bring home采用数量较少、规模较大的集群，部署和维护相对集中。

DNS可通过别名和解析结果将请求导向CDN节点，清单及应用调度也可参与节点选择。选择时应综合地理距离、链路拥塞和服务器负载，地理最近节点不一定具有最优访问性能。

#### 2.13 套接字编程与API调用过程

| UDP 服务器 | UDP 客户 |
|---|---|
| socket(SOCK_DGRAM) → bind → recvfrom → sendto | socket → sendto(数据,服务器地址) → recvfrom → close |

UDP 每次发送通常指定目的地址；服务器可用同一个 socket 与多个客户交换报文。

| TCP 服务器 | TCP 客户 |
|---|---|
| socket(SOCK_STREAM) → bind → listen → accept → 在新连接 socket 上收发 → close | socket → connect → 收发字节流 → close |

TCP `accept` 返回连接 socket；关闭该连接 socket 不等于关闭监听 socket。TCP 一次 `recv` 不保证恰好返回应用一次 `send` 的全部内容，应用必须自行处理消息边界和接收长度。

#### 2.14 补充：文件传输协议FTP

2026年第二章课件未详细展开FTP，本节依据期中大抄作为补充。FTP使用TCP，控制连接传输命令和响应，数据连接传输文件或目录。控制连接通常在会话期间保留，各次数据传输使用单独的数据连接，这种方式称为带外控制。

基本模型：同一会话下载 4 个文件，通常共 1 条控制连接 + 4 条数据连接 = 5 条 TCP 连接。控制端口 21；传统主动模式的数据连接使用服务器端口 20，**不是所有 FTP 数据连接都固定使用端口 20**。FTP 服务器需要维护会话状态。

### 第3章：传输层

#### 3.1 传输层服务、多路复用与解复用

网络层提供主机之间的逻辑通信，传输层进一步提供进程之间的逻辑通信。**进程间交付是传输层的基本功能**，可靠传输则取决于所采用的传输协议，UDP本身不提供可靠交付。

多路复用：发送端收集多个 socket 的数据，加上传输层控制信息，交给网络层。解复用：接收端根据地址、端口等信息，把数据交给正确 socket。

| 课程的解复用模型 | 识别端点的关键信息 | 结果 |
|---|---|---|
| 普通未连接 UDP socket | 目的 IP + 目的端口 | 不同源主机、不同源端口的报文可以交给同一个 UDP socket |
| TCP 连接 socket | 源 IP、源端口、目的 IP、目的端口 | 不同四元组区分不同 TCP 连接 |

源端口标识发送端通信端点，使服务器能够将响应发送至相应客户。普通UDP解复用不要求为各来源分别建立连接状态。

**同一服务器端口可支持多条TCP连接。** 各连接由源IP、源端口、目的IP和目的端口组成的四元组区分；即使服务器端口均为80，只要四元组不同即可建立独立连接。每条TCP连接仍是点到点连接。

#### 3.2 无连接传输协议UDP

UDP 不建立连接，不负责重传、不保证按序、不提供流量控制和拥塞控制。它主要提供端口解复用与差错检测，适合简单请求/响应，或由应用自行决定可靠性、时效性的场景。

首部共 8 B，四个字段各 16 bit：

| 字段 | 用途 |
|---|---|
| 源端口 | 标识发送端通信端点 |
| 目的端口 | 标识接收端套接字，用于解复用 |
| 长度 | UDP 首部 + 数据的总字节数 |
| 检验和 | 检测数据传输中的错误 |

如果 UDP 载荷为 100 B，UDP 长度是 108 B，不含 IP 首部。

**UDP的主要特点：** 首部较小，无连接建立过程，连接状态开销低，应用可以更直接地控制数据报内容与发送时机。TCP发送还受到流量控制、拥塞控制及组段策略等机制的约束。

应用可在UDP之上增加可靠传输机制。视频应用的传输协议也因系统设计而异，课件中的DASH采用基于HTTP的流式传输。

#### 3.3 因特网检验和

检验和计算将待校验内容划分为16bit字，进行反码加法，并将最高位溢出进位回卷至最低位，最后对结果按位取反。接收端将数据与检验和共同求和，校验通过时结果为全1。

**例：** 两个 16 bit 字 `0xF000` 和 `0x3001`：

1. 普通和为 `0x12001`。
2. 回卷进位：`0x2001 + 1 = 0x2002`。
3. 取反：检验和 `0xDFFD`。
4. 接收端 `0xF000 + 0x3001 + 0xDFFD` 回卷后为 `0xFFFF`。

UDP校验范围包括伪首部、UDP首部和数据。伪首部包含源、目的IP地址等信息，用于检测误投递，**伪首部仅参与检验和计算，不作为额外的UDP首部发送**。计算时检验和字段置0；数据长度为奇数字节时，在校验计算中补0。

检验和能检错，却不能纠错，也不能保证发现所有错误。检验和正确，不等于身份可信或数据没有遭到恶意修改。

#### 3.4 可靠数据传输的基本机制

| 机制 | 对应问题 | 作用 |
|---|---|---|
| 检错编码 / 检验和 | 数据可能存在未被识别的比特差错 | 检测传输差错 |
| ACK等反馈 | 发送方缺少接收状态信息 | 通告接收状态 |
| 重传 | 检测到差错或丢失后需要恢复数据 | 重新发送受损或丢失的数据 |
| 定时器 | 数据或ACK丢失后可能无法收到反馈 | 长时间无有效反馈时触发恢复 |
| 序号 | 重传产生重复，接收方可能重复交付 | 区分新旧数据、重复数据及顺序 |

**序号同时用于顺序识别和重复检测。** 即使停等协议仅允许一个分组未确认，ACK丢失也可能导致该分组重传，因此接收方仍需根据序号避免重复交付。

接收方无法直接检测尚未到达的分组。丢包通常通过发送端超时，或后续分组暴露的序号间隙进行推断。

#### 3.5 可靠数据传输协议rdt1.0—rdt3.0

| 版本 | 信道假设 | 使用的机制 | 局限 |
|---|---|---|---|
| rdt1.0 | 完全可靠 | 发送与接收即可 | 不能处理错误 |
| rdt2.0 | 可能发生比特差错，不丢包 | 检验和、ACK/NAK、差错重传 | 未处理ACK/NAK损坏 |
| rdt2.1 | 反馈也可能损坏 | 为分组分配0/1序号进行重复检测，ACK/NAK携带相关序号 | 仍未处理丢包 |
| rdt2.2 | 同上 | 使用重复ACK代替NAK，确认最近正确接收的分组 | 仍未处理丢包 |
| rdt3.0 | 可能出错，也可能丢包 | 在 2.2 基础上增加定时器、超时重传 | 停等效率低 |

**交替位协议的序号空间：** 停等协议仅有一个未确认分组，接收方只需区分当前分组与上一分组的重传，因此0/1序号能够满足重复检测要求。课程模型假设旧分组不会跨越多个序号周期仍然存活。

NAK表示当前分组未正确接收；rdt2.2用对最近正确分组的重复ACK表达同一状态。rdt3.0发送端通常忽略损坏或不匹配的ACK，等待有效ACK或定时器超时。

##### 停等协议的发送端与接收端状态转换

发送方等待上层数据，构造seq=0的分组，发送后启动定时器并等待ACK0。正确收到ACK0后转入seq=1的发送状态；超时则重传seq=0；损坏或不匹配的ACK不引起状态推进。

接收方期待seq=0时，对正确的新分组交付数据并返回ACK0，随后转为期待seq=1；收到重复的seq=0时仅返回ACK0，不重复交付。两个序号的处理规则对称。

**ACK丢失：** 发送方超时后重传已被接收的数据，接收方检测重复并再次返回ACK。**过早超时：** 即使原分组和ACK均未丢失，也可能触发重传；序号与去重机制确保数据不被重复交付。

**仅使用NAK的局限：** 稀疏数据传输或末尾分组丢失时，接收方可能无法通过后续分组发现缺失，恢复不能及时启动。连续传输且丢包较少时，NAK机制可减少反馈开销，但仍需处理传输结束和缺失检测问题。

#### 3.6 停等利用率、流水线与窗口大小

设数据包 L bit，链路 R bit/s，ACK 发送时间忽略，RTT 表示来回传播时间：

`t_tx = L/R`

`U_停等 = t_tx/(RTT+t_tx)`

停等协议每个周期仅有t_tx用于发送数据，其余时间等待反馈，因此在RTT较大而传输速率较高的链路上利用率较低。

窗口为 W 个分组时，理想无损信道：

`U_窗口 = min(1, W×t_tx/(RTT+t_tx))`

完全利用链路所需的最小窗口满足：`W ≥ ceil(1 + RTT/t_tx)`。

**公式适用条件：** 利用率上限为1。若题设RTT已包含数据发送时间，应根据其定义计算反馈周期，避免重复加入t_tx；ACK传输时间不可忽略时，还应计入相应时间。

#### 3.7 回退N步与选择重传协议

流水线协议允许多个分组同时处于未确认状态。base为最早未确认分组的序号，next为下一新分组的序号。发送窗口包括已发送未确认的序号和允许发送但尚未发送的序号，窗口外的新分组暂不能发送。

| 项目 | GBN（回退 N 步） | SR（选择重传） |
|---|---|---|
| ACK含义 | 课件中ACK n累计确认至分组n | ACK n单独确认分组n |
| 乱序正确分组 | 丢弃并返回最近一次按序确认 | 缓存窗口内的正确分组并单独确认 |
| 上层交付 | 按序 | 缓存乱序分组后仍按序交付 |
| 定时器 | 一个定时器对应最早未确认分组 | 每个未确认分组具有逻辑定时器 |
| 超时重传 | 重传最早未确认分组及其后已发送的未确认分组 | 仅重传相应超时分组 |
| 实现取舍 | 接收端简单，重传代价可能大 | 缓存、标记和定时器较复杂，少做重复传输 |

**GBN的重传数量取决于实际未确认分组数量。** 定时器超时后重传已发送未确认的分组，不包含窗口内尚未发送的新分组，因此重传数不一定等于窗口大小N。

**SR的窗口移动：** 收到窗口内非基序号分组的ACK时，仅标记该分组已确认。基序号分组被确认后，发送窗口跨过其后连续已确认的序号区间。

##### 示例：分组0、1、2、3中分组1丢失

GBN：正确接收分组0并返回ACK0；分组2、3因乱序被丢弃，分别触发ACK0；分组1超时后，发送端重传分组1、2、3。

SR：正确接收分组0并返回ACK0；缓存分组2、3并分别返回ACK2、ACK3；分组1超时后仅重传分组1，接收端随后连续交付分组1、2、3。

##### 窗口大小与序号空间

m bit 序号有 K=2^m 个值。

- GBN：`W_发送 ≤ K-1`，所以 `m ≥ ceil(log2(W+1))`。
- SR：等大发送/接收窗口时 `W ≤ K/2`，所以 `m ≥ ceil(log2(2W))`。

SR缓存乱序分组。若窗口超过序号空间的一半，序号回绕后旧分组可能落入新的接收窗口并被错误地识别为新数据。因此需要保证相关旧窗口与新窗口不重叠。**序号位数计算应明确采用GBN还是SR。**

一般非等大窗口时，避免这种歧义需要序号空间至少覆盖发送窗口和接收窗口之和；课程通常讨论两者等大。

#### 3.8 TCP服务模型与报文段结构

TCP 是面向连接、全双工、点到点的可靠有序字节流。双方都维护缓存和状态；全双工意味着两方向可同时传输，各方向有自己的序号、ACK、流量和拥塞控制状态。

**TCP不保留应用消息边界。** 应用依次写入100B和200B时，接收方可能分两次读取50B和250B，或采用其他划分。TCP保证字节内容及顺序，应用应通过长度字段、分隔符等机制确定消息边界。

| TCP 首部字段 | 主要作用 |
|---|---|
| 源/目的端口，各 16 bit | 解复用与回送 |
| seq，32 bit | 本段第一个数据字节的序号 |
| ack，32bit | 接收方期望从对端获得的下一个字节序号 |
| 首部长度 | 给出TCP首部长度及数据起始位置，单位为4B |
| ACK 标志 | ack 字段是否有效 |
| SYN / FIN | 建立连接 / 关闭该发送方向 |
| RST | 拒绝、复位连接等 |
| 接收窗口rwnd | 通告接收端可用缓存空间，用于流量控制 |
| 检验和 | 检测首部和数据错误 |
| URG / 紧急指针 | 传统紧急数据标记机制，作为补充识记 |
| ECE / CWR | ECN 相关拥塞反馈 |
| 选项 | MSS、窗口缩放、SACK 等 |

基本首部 20 B，有选项时更长，最大通常 60 B。MSS 是**一个 TCP 段可携带的数据字节数**，不包含 TCP/IP 首部，不等于 IP 数据报总长。

SACK 选项报告已经收到的非连续数据块；普通 ack 字段仍表示连续收到之后的下一个字节，不会因为 SACK 就改变含义。

窗口缩放可把通告值乘以 `2^scale`。拥塞窗口 cwnd 是发送端内部状态，**不是 TCP 头里那个“接收窗口”字段**。

#### 3.9 TCP序号与确认号

seq=s、载荷长度 l，携带的字节范围是 `[s, s+l-1]`，下一份新数据起始序号是 s+l。

**累计确认：** ACK=y表示y之前的数据已连续正确接收，接收方期望的下一个字节序号为y。确认号不等于最后接收字节的序号，也不表示报文段的编号。

**例：** 接收方期待序号100，收到seq=100、长度50B的段后，确认号为150。若先收到seq=150、长度50B的段，由于100–149尚未收到，确认号仍为100。待缺失区间补齐，若150–199已缓存，确认号可推进至200。

因此，收到 seq=90、100 B 的段之后，ack **不一定是 190**：

- 前面没有缺口、后面没有已缓存连续数据：190。
- 前面缺数据：可能小于 90。
- 本段补齐缺口，后面还有已缓存连续数据：可能大于 190。

##### 双向通信中的序号与确认号

A→B报文段的seq编号A发送的数据，ack确认B→A的数据。B返回纯ACK时，seq为本方向当前的下一发送序号，发送纯ACK本身不消耗序号。

例如，本方向下一发送序号为70，且报文段不携带数据、SYN或FIN时，纯ACK使用seq=70，无需递增至71。

**序号消耗规则：** 数据每个字节占 1；SYN 占 1；FIN 占 1；普通纯 ACK 不占序号。

##### 部分重叠报文段的处理

设接收方期待序号x，收到字节区间`[80,99]`。当x=90时，80–89属于重复数据，90–99仍为新数据。处理时还应检查接收窗口及已缓存数据，不能仅根据首字节序号小于期望值判定整段重复。

#### 3.10 TCP 的可靠传输、计时、快速重传

课程简化模型：累计确认；通常缓存乱序数据；一个重传定时器关注最早未确认的数据；超时后优先重传最早未确认段；连续收到 3 个重复 ACK 可以快速重传缺失段。

**ACK丢失不必然导致重传。** 后续累计ACK可覆盖先前数据的确认；若有效确认未在RTO内到达，则可能触发超时重传。接收方通过重复检测避免再次交付已收到的数据。

重复ACK应相对于当前SendBase判定。首次推进SendBase的ACK是新确认；在当前确认号不变的条件下再次收到相同确认，才计为重复ACK。仅统计报文中的相同数值不足以判断快速重传条件。

TCP结合了GBN和SR的部分机制：通常缓存乱序数据，超时后优先重传最早未确认段；普通ACK采用累计确认，课程模型使用一个重传定时器。因此TCP既不等同于GBN，也不等同于SR。

##### RTT估计与重传超时设置

RTO过短会产生不必要重传，过长则延长丢失恢复时间。课件采用以下估计公式：

`EstimatedRTT = (1-α)×旧EstimatedRTT + α×SampleRTT`，α 常取 1/8。

`DevRTT = (1-β)×旧DevRTT + β×|SampleRTT-EstimatedRTT|`，β 常取 1/4。

`RTO = EstimatedRTT + 4×DevRTT`

SampleRTT为报文段发出至相应ACK到达的时间样本。按课件计算DevRTT时使用本次更新后的EstimatedRTT；题目另有更新顺序约定时，以题设为准。

**例：** 旧估计 100 ms，旧偏差 10 ms，样本 120 ms。新估计 102.5 ms；新偏差 `0.75×10+0.25×17.5=11.875 ms`；RTO=150 ms。

**Karn算法：** 重传段的ACK可能对应原始发送或重传，存在RTT测量二义性。课程方法是不使用这类ACK更新RTT样本，并在超时后对RTO进行指数退避。

**快速重传与超时退避应区分。** RTO翻倍属于超时恢复策略，不能将其推广到所有重传事件。

##### 延迟 ACK

延迟ACK允许接收方暂缓反馈，以便累计确认连续到达的报文段并减少确认开销。课程模型的等待上限为500ms，至少每两个满尺寸报文段确认一次。检测到序号间隙、缺失区间被填充或重复段到达时，应及时发送确认。

#### 3.11 TCP流量控制

TCP 接收缓存被尚未被应用读取的数据占用，课程模型：

`rwnd = RcvBuffer - (LastByteRcvd-LastByteRead)`

接收端通过TCP首部中的rwnd通告可用缓存，发送端据此限制未确认数据量。数据被TCP确认仅表示已到达接收端，并不意味着应用已经读取；已确认数据仍可能占用接收缓存。

**零窗口通告与探测：** rwnd=0时发送端暂停普通新数据传输，并通过零窗口探测触发接收端重新通告窗口，避免窗口更新报文丢失造成持续等待。

**糊涂窗口综合症：** 接收端频繁通告很小的窗口，可能导致发送端不断传输短报文段，增加首部开销。接收端可在可用空间达到一个MSS或接收缓存一半的较小值后，再通告增大的窗口。

**Nagle算法：** 无未确认数据时可立即发送小段；存在未确认数据时，缓存后续小数据，直至累计达到MSS或此前数据得到确认后发送。发送仍受流量控制和拥塞控制约束，其等待条件由数据量和网络反馈共同决定。

应用产生数据的速率超过网络发送速率时，发送缓存可能填满，应用写入套接字将受到阻塞或反压。这一限制即使在无丢包且接收端处理较快时也可能发生。

#### 3.12 流量控制与拥塞控制的关系

| 比较 | 流量控制 | 拥塞控制 |
|---|---|---|
| 控制对象 | 接收端缓存与应用读取能力 | 网络链路和路由器的承载能力 |
| 反馈方式 | 接收端显式通告rwnd | 端系统根据丢包/延迟推断，或使用显式网络反馈 |
| 对应窗口 | rwnd | cwnd |

流量控制避免接收缓存溢出，拥塞控制避免过量数据进入网络。接收端应用读取较慢时，rwnd可能限制发送；瓶颈链路负载较高时，cwnd可能限制发送。

`FlightSize = 已发送但尚未累计确认的字节数`

`当前有效上限 = min(rwnd, cwnd, 题目另给的本地限制)`

`可新增发送量 = max(0, 当前有效上限-FlightSize)`

**2024 选择题：** 本地限制64 KB，cwnd32 KB，rwnd40 KB，已发未确认30 KB：最多再发 `min(64,32,40)-30 = 2 KB`。MSS4 KB 是最大载荷，不是最小载荷，因此允许发一个2 KB段。

课程模型通常以`FlightSize ≤ min(rwnd,cwnd)`表示发送约束。窗口缩小时，既有在途数据可能暂时超过新的窗口上限；发送端应限制后续新数据注入，直至在途量满足相应约束。

#### 3.13 TCP连接建立与三次握手

设 A 初始序号 x，B 初始序号 y，不携带应用数据：

| 步骤 | 方向 | SYN | ACK 标志 | seq | ack |
|---|---|---|---|---|---|
| 1 | A→B | 1 | 0 | x | ACK标志未置位，字段无效 |
| 2 | B→A | 1 | 1 | y | x+1 |
| 3 | A→B | 0 | 1 | x+1 | y+1 |

SYN 占一个序号。第三步可以携带数据，若没有数据，其 ACK 本身不再消耗序号。

**三次握手的必要性：** 延迟到达的旧连接请求可能导致服务器错误建立连接。第三次确认用于验证客户端确已收到本次服务器响应，并确认服务器的起始序号。

固定起始序号会增加旧连接残留报文与新连接数据混淆的风险。课件通过时钟和足够大的序号空间说明序号选择原则；具体实现可采用不同算法。

状态简记：客户端 CLOSED→SYN_SENT→ESTABLISHED；服务器 LISTEN→SYN_RCVD→ESTABLISHED。

#### 3.14 TCP连接关闭

A发送FIN表示终止A→B方向的数据发送，B→A方向仍可继续传输。典型关闭过程为A发送FIN、B确认、B发送FIN、A确认；其中部分ACK与FIN可合并，因此不一定使用四个独立报文段。

主动关闭方：ESTABLISHED→FIN_WAIT_1→FIN_WAIT_2→TIME_WAIT→CLOSED。

被动关闭方：ESTABLISHED→CLOSE_WAIT→LAST_ACK→CLOSED。

主动关闭方通常在TIME_WAIT状态等待2MSL，以便在最后ACK丢失时响应重传FIN，并使旧连接残留报文失效。FIN与SYN均消耗一个序号。

SYN洪泛通过大量未完成握手消耗服务器半连接状态及资源。SYN扫描中，SYNACK通常表示端口接受连接，RST通常表示拒绝连接；无响应还可能由丢包或过滤造成。FIN扫描结果与系统实现有关。

#### 3.15 拥塞的原因与代价

路由器输入流量接近或超过输出能力时，排队延迟增大；缓存溢出导致丢包，重传进一步增加负载。过早超时引起的不必要重传降低资源利用率；分组在下游被丢弃还会浪费其已占用的上游链路与缓存资源。

网络发送量与应用有效吞吐量不同。重复数据占用容量但不增加有效交付量，严重拥塞时继续增大发送负载可能降低有效吞吐量。

拥塞控制可分为端到端控制和网络辅助控制。前者由终端依据丢包、延迟等推断拥塞，后者由网络设备提供显式反馈。经典TCP以丢包作为主要拥塞信号，但丢包也可能来自无线差错等非拥塞原因。

#### 3.16 TCP慢启动、拥塞避免与快速恢复

下面使用课件及真题的经典 TCP 模型：初始 cwnd=1 MSS，按轮次近似增长，ssthresh 是慢启动阈值。现代实现的初始窗口等参数可能不同，考试用题目给定值。

| 状态 / 事件 | 机制 | 窗口更新规则 |
|---|---|---|
| 慢启动，cwnd<ssthresh | 随新确认指数增大窗口 | 每个新ACK约增加1MSS，一轮约翻倍 |
| 拥塞避免，cwnd≥ssthresh | 以加性增长探测可用容量 | 每RTT约增加1MSS，每ACK可近似增加MSS²/cwnd |
| 超时 | 降低发送负载并重新慢启动 | ssthresh取丢包前窗口的一半，再令cwnd=1MSS |
| Reno 收到3个重复ACK | 快速重传并进入快速恢复 | ssthresh=旧cwnd/2；cwnd=ssthresh+3MSS |
| 快速恢复中收到额外重复ACK | 推断又有后续数据到达接收端 | cwnd增加1MSS，窗口允许时可发送新数据 |
| 快速恢复收到推进确认的新ACK | 确认缺失区间已恢复 | cwnd调整为ssthresh，退出快速恢复并进入拥塞避免 |
| Tahoe 收到3个重复ACK | 快速重传但无快速恢复 | ssthresh=旧cwnd/2；cwnd=1 MSS，再慢启动 |

慢启动从较小窗口开始，以避免在未知网络条件下注入大量数据；其名称描述的是初始发送策略，增长规律则为近似指数增长。

Reno对重复ACK和超时采用不同响应。重复ACK表明后续段仍能到达，网络保留一定交付能力；超时可能意味着更严重的拥塞或交付中断。

**快速恢复的窗口应分阶段分析：** 进入快速恢复时cwnd为`半窗口+3MSS`，退出恢复后回到半窗口。仅展示各轮稳定窗口的图表可能省略临时膨胀过程。

**ssthresh应依据丢失检测前的窗口计算，再重置cwnd。** 若先将cwnd置1再计算一半，将错误地改变阈值。

阈值恰好相等时本讲义按2026课件采用拥塞避免；其他图题可能把到达阈值的端点计入上一段增长区间，答题应说明所指是“该轮发送状态”还是“通往该点的增长阶段”。

规范实现还会考虑实际 FlightSize、最小阈值和额外恢复算法；本课程的轮次题主要用上述模型。快速恢复期间是否能发新分组，仍须检查在途数据，不能直接把 cwnd 当成本轮新发送分组数。[经典拥塞控制及快速恢复机制](https://www.rfc-editor.org/rfc/rfc5681.html)

#### 3.17 拥塞窗口图与轮次计算方法

1. 明确RTT、MSS、初始窗口、阈值、算法类型及ACK策略。
2. 按轮次列出起始cwnd、未确认量、实际发送序号范围和累计新数据量。
3. 指数增长段识别慢启动，线性增长段识别拥塞避免。
4. 丢包后降到1通常是超时/Tahoe恢复；降到半窗口通常是Reno快速恢复完成。必须结合题目算法。
5. 确定第k段所属轮次时，累计各轮新发送的报文段数，重传不计入新的文件数据量。
6. 明确计时起点与终点，区分连接建立、最后数据接收及最后ACK返回等阶段。

**若第1轮在t=0开始，共需n轮，忽略发送时间，对称路径上：**

- 最后一轮开始时间：`(n-1)RTT`。
- 最后数据到接收端：`(n-1)RTT + RTT/2`。
- 最后确认回到发送端：`nRTT`。

例：各轮窗口依次为1、2、4、8、9、10，传输30个报文段。前五轮新发24段，第六轮新发6段；RTT为10ms时，最后数据在55ms到达接收端，最终ACK在60ms返回发送端。

快速恢复期间应结合FlightSize分析发送空间。已缓存但尚未累计确认的乱序数据仍计入未确认量，不能直接用cwnd代替本轮可发送的新数据量。2024年相关题目详见配套解析。

#### 3.18 TCP 平均吞吐量、公平性和新机制

忽略慢启动，稳定的Reno锯齿在W/2到W之间变化，W若为字节：

`平均吞吐量 ≈ 0.75W/RTT`

W以报文段数表示时，应乘以MSS；换算为bit/s时应统一字节和比特单位。

丢包率p、固定RTT、经典稳态模型下：

`平均吞吐量 ≈ 1.22MSS/(RTT×sqrt(p))`

它描述丢包率上升或RTT变大时吞吐量降低，不是任何网络场景下都精确成立。推导见指定作业P47。

**公平性：** 参数相近的K条TCP连接共享速率R的瓶颈链路时，目标是每条连接获得约R/K的平均速率。加性增减小相对吞吐量差异，乘性减保持各连接速率比例，使反复调整趋向公平分配。

公平性受RTT、MSS和拥塞算法等因素影响。应用通过多条并行连接可能获得更大总份额，因此连接间公平不等于应用间公平；不响应拥塞的UDP流也可能破坏与TCP之间的公平分配。

**CUBIC：** 采用不同于线性AIMD的窗口增长函数，提高高速、长时延场景下的容量探测效率。本章主要掌握其设计动机。

**ECN：** 路由器在IP分组中标记拥塞，接收端通过TCP的ECE标志反馈，发送端降低窗口并以CWR表示已响应。该机制通过显式标记提供拥塞信号。

**QUIC：** 基于UDP实现可靠传输、拥塞控制与安全握手，并支持多个流独立有序交付。课件将其作为应用侧实现传输功能的例子，重点是理解UDP、QUIC与HTTP之间的协议关系。

应掌握ACK丢失与停等恢复、GBN和SR丢包过程、TCP累计确认和乱序处理、三次握手及连接关闭，并能够分析慢启动、拥塞避免、超时和三次重复ACK引起的窗口变化。各机制均应结合其服务目标与执行条件解释。

### 二、第1章作业：网络性能与分组交换

#### P9：统计复用与用户容量

链路1 Gbps，每个活跃用户100 kbps，独立活跃概率p=0.1。

电路交换为每个用户预留100 kbps：`N = 10^9/10^5 = 10000`。

分组交换有M个用户，活跃人数X服从二项分布：

`P(X>N) = Σ_{k=N+1到M} C(M,k)p^k(1-p)^(M-k)`

也可写成 `1-Σ_{k=0到N} C(M,k)p^k(1-p)^(M-k)`。M≤N时概率为0。

所求事件为活跃用户数大于N，因此求和下限为N+1。分组交换依赖统计复用，在一定的过载概率约束下可支持更多用户，但不保证所有用户同时活跃时链路仍不过载。

#### P10：三条链路上的单分组端到端延迟

两台交换机，三条链路，无排队：

`T = Σ_{i=1到3}(L/R_i + d_i/s_i) + 2d_proc`

L=1500 B=12000 bit；各链路2.5 Mbps；传播速度2.5×10^8 m/s；三段距离5000、4000、1000 km；每台交换机处理3 ms。

- 传输：每跳4.8 ms，共14.4 ms。
- 传播：20+16+4=40 ms。
- 处理：2×3=6 ms。
- 总共 **60.4 ms**。

该路径包含3条链路和2台中间交换机，处理中间节点的次数为2。

#### P13：同时到达分组的平均排队延迟

N个等长包到达空出口，排队等待依次为0、L/R、…、(N-1)L/R。

`平均排队时间 = (N-1)L/(2R)`。

若每隔NL/R又到来同样一批，上一批恰好发完，每批重复同一过程，长期平均仍相同。若还问平均发完时间，则加L/R，得到`(N+1)L/(2R)`。

#### P21：多条链路互不重叠路径的吞吐量

第k条路径的瓶颈速率`B_k=min_i R_ki`。

- 只能选一条路径：`吞吐量=max_k B_k`。
- 可同时利用全部M条互不共享链路的路径：理想模型下`吞吐量=Σ_k B_k`。

单条路径的吞吐量由最小链路速率决定；只选一路时取各路径吞吐量的最大值，全部并行使用时取总和。若路径共享链路或端系统存在总速率限制，则需另行计入相应约束。

#### P22：链路丢包概率与平均重传次数

共N条链路，每条独立丢包概率p，则一次端到端成功概率`q=(1-p)^N`。

每次完整尝试也假设独立时：

- 平均总发送次数：`1/q`。
- 平均重传次数：`1/q-1`。

“重传次数”不含第一次发送。若N=2、p=0.1，q=0.81，平均总发送约1.2346次，平均重传约0.2346次。

#### P25：带宽时延积与比特的空间长度

本地英文8版原题：距离20000 km，R=5 Mbps，s=2.5×10^8 m/s，文件800000 bit。

1. 单向传播时间：`2×10^7/(2.5×10^8)=0.08s`。
2. BDP：`5×10^6×0.08=400000 bit`。
3. 连续发送时，链路内最多有`min(文件长度,BDP)=400000 bit`。
4. 一个比特空间长度：`s/R=50m`。
5. 一般表达式是s/R，距离不直接决定这个宽度。

**注意解答册给过125m，与这里R=5Mbps的原题不一致；按本题参数应为50m。**

#### P31：报文分段与流水线传输

本地英文8版题目：文件10^6 bit，三跳，各5 Mbps，切成100个10000 bit的包。

- 不切：到第一交换机0.2s；存储转发三跳，共0.6s。
- 切包：每个分组发2ms；第一包到第一交换机2ms；第二包到第一交换机4ms。
- 全部100包到目的端：`(100+3-1)×2ms=204ms`。

分段使不同链路能够并行传输不同分组，降低整体完成时间；差错恢复时仅需重传相应分组，也可降低长分组对其他流量的阻塞。代价包括首部开销增加、排序重组及处理负载。

解答册部分段落使用800个分组、5ms等参数，与本题条件不一致，应以本地教材原题为准。

#### P33：固定首部开销下的最优分组长度

文件长度Fbit，每段有效数据Sbit，首部80bit，分组长度为S+80，经过3条速率为Rbps的链路。忽略传播与排队，假设F/S为整数或采用连续近似：

`T(S) = (F/S+2)(S+80)/R`

展开：`T(S)=[F+80F/S+2S+160]/R`。

S小：包多，重复首部多；S大：每个包完成三跳流水线的启动/收尾成本大。最优点使两类增量平衡：

`dT/dS = (-80F/S²+2)/R = 0`

所以 **`S*=sqrt(40F)` bit**。实际若有限制、F不能整除S，则用ceil(F/S)，并检查邻近可行分组大小，连续解作为候选。

#### P9：缓存命中率与接入链路排队

题目借用教材图2.12的15Mbps出口，平均对象1Mb，每秒16个请求，平均远端Internet延迟3s，公式`T_access=Δ/(1-bΔ)`。

`Δ=1Mb/15Mbps=1/15s`；无缓存时`bΔ=16/15>1`。

**a：该模型不存在有限的稳态平均响应时间。** 因为ρ>1，无限缓存下队列持续增长，有限缓存则会溢出丢包。公式Δ/(1-bΔ)仅适用于稳定条件，不能通过改变分母符号得到有限延迟。解答册给出的约3.099s不符合本题模型。

**b：未命中率0.4，因此只有40%请求通过出口。**

- 出口到达率`b'=0.4×16=6.4/s`。
- 出口流量强度`ρ'=6.4/15=0.426666…`。
- 未命中的接入时间`(1/15)/(1-6.4/15)=1/8.6≈0.116279s`。
- 未命中响应时间`3+0.116279=3.116279s`。
- 命中时间忽略，则全体平均`0.4×3.116279≈1.246512s`。

**本题结果约为1.247s。** 解答册的0.038s接入延迟和1.215s总体延迟未按本题参数正确代入。不同教材版本使用不同出口速率时，应分别计算。

### 四、第3章作业：窗口、可靠传输和拥塞

#### P15：目标利用率下的发送窗口

教材例子的R=1Gbps、RTT=30ms；本题包1500B，因此`t_tx=12μs`。

`U=min(1,W×12/(30000+12))`。

要求U>0.98：`W>0.98×2501=2450.98`，最小整数 **2451个包**。若问完全填满，则至少2501个包。

#### P22：发送窗口与在途ACK的可能范围

本地英文8版是GBN发送窗口 **N=4**，序号空间1024，信道不重排。

接收端期待序号k，说明数据已按序接收至k-1。相关ACK可能已到达发送端，也可能仍在返回链路上传播。

**a：** 发送窗口形如`[b,b+3]`，其基序号可能在`k-4≤b≤k`之间，按1024取模解释。

- 最近4个包的ACK都未到：窗口可能仍是`[k-4,k-1]`。
- ACK已全部到：可滑到`[k,k+3]`。
- 部分ACK已到：在二者之间。

**b：** 在GBN的ACK n表示“收至n”口径下，可能仍在返回途中的是`k-5`至`k-1`，按模1024。`k-5`可能是先前包重发后产生的重复确认；更旧的ACK在“不重排”条件下，不能还落在已使发送方推进的后续反馈之后。

若只考虑各包第一次产生的ACK，可写最近未确认的范围`[k-4,k-1]`，但完整问法“所有可能报文”还要考虑重复ACK。解答册将窗口写成3，是参数不一致；这里按N=4推广。

#### P23：最大窗口与序号空间

K个序号：GBN最大发送窗口K-1；SR等大发送/接收窗口最大floor(K/2)。理由见讲义：SR需要新、旧窗口不发生混淆。若给m个bit，先计算K=2^m再比较。

#### P25：UDP对报文内容与发送时机的控制

**报文内容：** UDP将应用提交的消息作为一个数据报的载荷，保留消息边界；TCP提供字节流服务，可将消息划分到多个段，或将相邻消息中的字节组合在同一段中。

**发送时机：** UDP没有TCP流量控制和拥塞控制引入的等待。TCP数据可能暂存在发送缓存，待窗口允许后发送；UDP发送仍受内核队列、网卡和网络负载等因素影响。

#### P27：两段数据与累计ACK

B已经收至126；第一段seq127、80B，源端口302、目的80；第二段40B。

- a：第二段 **seq207、源302、目的80**。
- b：第一段先到，B回 **ACK207、源80、目的302**。
- c：第二段先到，前面127–206缺失，B回 **ACK127**。
- d：顺序到达但首ACK丢、次ACK迟于超时：B先发ACK207（丢）、再发ACK247（延迟）；A最早未确认段127超时，重发seq127的80B；B不重复交付，返回ACK247；A收到任意有效的累计ACK247，都能推进到247。

本题应标出ACK247的延迟。数据段均已到达接收方，超时仅需重传seq127对应的段，首个ACK丢失不要求重传全部数据。

#### P37：GBN、SR与TCP的单分组丢失恢复

这里用“包1–5”比较，TCP一列把每分组长度度抽象为一个序号单位；真实TCP按字节编号。

| 协议 | A发送的数据包 | 总发送数 | B发送的ACK | ACK总数 |
|---|---|---|---|---|
| GBN | 初发1–5；重发2–5 | 9 | ACK1共4次，然后ACK2、3、4、5 | 8 |
| SR | 初发1–5；只重发2 | 6 | ACK1、3、4、5，再ACK2 | 5 |
| TCP，无延迟ACK | 初发1–5；快速重传2 | 6 | ACK2共4次，再ACK6 | 5 |

GBN的ACK1意为“收至包1”；TCP的ACK2意为“想要下一个单位2”。这两列差1是编号语义不同。

首个ACK2是新的确认，后三个是重复ACK，足以触发TCP快速重传。若RTO远大于5RTT，则TCP不用等超时，最快；SR课程模型仍等待包2定时器。

#### P47：从锯齿推导丢包率与吞吐量

W以段为单位，假设W为偶数，一个周期窗口从W/2逐轮加1到W，周期末丢1个包。

`周期发送包数 = Σ_{w=W/2到W}w = (W/2+1)×3W/4 = 3W²/8+3W/4`

所以`p=1/(3W²/8+3W/4)`。

W大时忽略一次项：`p≈8/(3W²)`，即`W≈sqrt(8/(3p))`。

平均窗口0.75W，平均吞吐量：

`0.75W×MSS/RTT ≈ 1.2247MSS/(RTT×sqrt(p))`。

本节以p表示丢包率，与用于分组长度的符号区分，以避免量纲和含义混淆。

#### 思考题P24、41、42、43

#### 简答1：GBN窗口3，pkt1丢失

一种符合题意的时间线如下；ACK n按GBN口径表示收至n。

```text
A → B：pkt0                 B交付0，B → A：ACK0
A → B：pkt1（丢）
A → B：pkt2                 B仍期待1，丢弃2，返回ACK0
A收到ACK0，base变1，允许发pkt3
A → B：pkt3                 B仍期待1，丢弃3，返回ACK0
pkt1对应定时器超时
A → B：重传pkt1            B交付1，返回ACK1
A → B：重传pkt2            B交付2，返回ACK2
A → B：重传pkt3            B交付3，返回ACK3
```

具体箭头交叉位置取决于原图的传播时序，但应满足发送窗口及GBN接收规则。共发送7次数据分组，首次pkt1丢失。**初次到达的pkt2、pkt3属于乱序分组，GBN接收端将其丢弃。**

#### 简答2：可靠数据传输的基本机制及作用

检错编码检测比特差错；确认反馈接收状态；重传恢复损坏或丢失的数据；定时器在长期无有效反馈时触发恢复；分组序号识别顺序和重复数据，避免重复交付。各机制应结合其对应问题说明。

#### 简答3：电路交换、分组交换和Internet的选择

电路交换通信前预留资源，期间固定占用，性能相对稳定但静默期浪费；分组交换按需共享，适合突发流量，但可能排队、丢包，需要可靠传输和拥塞控制。Internet以突发数据应用为主，统计复用提高利用率并支持更多用户。

#### 简答4：给定起始序号的三次握手

| 段 | SYN | ACK标志 | seq | ack |
|---|---|---|---|---|

#### 简答5：服务器端口复用与TCP连接类型

**该结论不正确。** 服务器维护多条独立的点到点TCP连接，每条连接由源IP、源端口、目的IP和目的端口组成的四元组识别。服务器端口相同不影响不同四元组连接的区分。

#### 简答6：TCP确认段的五种作用

1. **确认数据：** ACK=y使发送方知道y以前连续数据已经收到，可移动SendBase并回收发送缓存。
2. **发现缺失：** 重复ACK表示连续数据有缺口，3个重复ACK可触发快速重传；长期无ACK则最终超时。
3. **设置超时：** 未重传段的发送到确认时间用于测量SampleRTT，更新RTT估计和RTO。
4. **流量控制：** 确认段的接收窗口字段通告对端剩余缓存空间；不只是ack数值在发挥作用。
5. **拥塞控制：** 新ACK驱动慢启动/拥塞避免增长，重复ACK触发减速与恢复，ACK节奏帮助限制发送；ECN也可由相关标志反馈。

#### 计算1：三种HTTP连接方式的耗时

若没有DNS成本、初始无TCP连接、对象同源、**非持久方案无并行连接**：

- 非持久：HTML2RTT，每图2RTT，总`2(n+1)RTT`。
- 持久无流水线：建连RTT+HTML请求RTT+n次图片RTT，总`(n+2)RTT`。
- 流水线持久：建连RTT+HTML请求RTT+一批图片请求RTT，总`3RTT`，n≥1。

原题未规定非持久HTTP的并行连接数。上述结果采用串行模型；若允许n条并行连接，总时间为4RTT；最多k条并行连接时为`2RTT+2ceil(n/k)RTT`。计算时应明确采用的连接及调度条件。

#### 计算2：窗口表1、2、4、8、9、10、5、6、1、2、3、4

MSS=1KB，原表按每轮批量发送、每轮后调整窗口。

- 拥塞避免轮次 **4–8、11–12**；第4轮窗口8、第11轮窗口3，恰好等于门限，按2026课件转拥塞避免。

ssthresh并非固定为初始8KB；丢失检测后会按当时窗口重新设置。

#### 计算3：卫星链路、停等、窗口和序号位数

R=10Mbps，单向传播250ms，L=50000bit；ACK发送时间忽略。因此`t_tx=5ms`，来回传播RTT=500ms。

1. 停等利用率：`5/(500+5)=1/101≈0.9901%`。
2. W=10时：`10×5/505=10/101≈9.901%`。
3. 满载所需最小窗口：`ceil(505/5)=101个包`。
4. 若GBN：`2^m≥102`，至少 **7bit**。
5. 若SR等大窗口：`2^m≥202`，至少 **8bit**。

原题未指定滑动窗口协议，因此序号位数取决于GBN或SR的确认与接收模型。另应区分比例与百分比：1/101≈0.0099，对应约0.9901%。

#### 简答1：接入网、网络核心和三类ISP

接入网连接端系统与边缘路由器；网络核心利用路由器和通信链路完成选路与转发；本地ISP为用户和机构提供接入；地区ISP汇聚并互联区域接入网络；第一层ISP提供广域互联并与其他骨干网络对等交换流量。

#### 简答2：固定路径上的时延抖动

主要来源是**排队延迟**。输出队列的积压程度随时间变化，即使路径和分组长度相同，不同分组的等待时间也可能不同。固定媒体、路径、分组长度及链路速率时，传播与传输延迟相对稳定；处理负载等条件变化也可产生附加波动。

#### 简答3：并行连接、流水线与缓存验证耗时

以下L按bit，R按bit/s；若L以B给出，用8L替代。DNS未计；第一次到源站的TCP连接需要建立；R是共同的瓶颈总带宽。

**(1) 流水线持久，无代理：** 建连T，取HTML T，取图片一批T，传n张图nL/R：

**`T_total=3T+nL/R`**。

**(2) n条并行非持久连接取图片：** HTML先2T，图片新连接握手一批T、请求/响应一批T，数据仍共享R：

**`T_total=4T+nL/R`**。

**(3) 缓存对象有效，但要求条件GET验证：** 不传输图片实体，但仍需完成远端验证。采用(1)的持久流水线模型、按HTML后引用对象的依赖次序且初始无代理至源服务器连接时，结果为**3T**；已有源服务器连接时为**2T**。串行验证或重复建立连接会增加时间。

原题(3)未明确代理至源服务器的连接状态及验证调度，故需列出计算假设。**条件GET需要远端响应，不能将其直接视为零开销。** 仅当缓存可直接提供有效副本且无需验证时，忽略局域网成本后响应时间可近似为0。

#### 简答5：TCP序号、确认号与重传时间线

原图首段A→B：seq92、ack70、8B，表示A发92–99。假设B期待92、B不发送应用数据，因此B的纯ACK用seq70；乱序数据按课件缓存。

**左图：第二段出错。**

| 原图标号 | 方向 / 内容 | seq | ack |
|---|---|---|---|
| ① | A→B，100B第二段 | 100 | 70 |
| ② | B→A，确认首段 | 70 | 100 |
| ③ | A→B，100B第三段 | 200 | 70 |

第二段100–199损坏，B丢弃；第三段200–299正确但有缺口，B缓存并立即回seq70、ACK100。A收到②后，SendBase由92推进到100，定时器针对最早未确认段100重启。后续重复ACK不推进SendBase，不重新按“最后一份新段”计时。

图中后续段不够产生3个重复ACK，需等定时器超时，重发seq100、ack70、100B。B补齐100–199，并已有200–299，回seq70、ACK300。时间线在A收到②的位置到超时重发位置标出seq100的计时区间。

**右图：第二段丢失，首个ACK也丢失。**

| 原图标号 | 方向 / 内容 | seq | ack |
|---|---|---|---|
| ① | B→A，收到seq200后重复确认 | 70 | 100 |
| ② | A→B，第四个数据段，100B | 300 | 70 |
| ③ | B→A，收到seq300后的确认 | 70 | 100 |

最初92–99正确到达，B的第一个ACK100丢失；100–199丢失；200–299、300–399先后到达并缓存。A收到图中①时，ACK100对当前SendBase92是**新的累计确认**，不是重复ACK，SendBase推进到100并重启定时器；③才是重复ACK。

图中有效ACK不足以产生3个重复ACK，不能触发快速重传。若无后续数据，则等待seq100超时并重传100–199；接收端补齐缺失区间后累计确认至400。计时区间从A收到①并将SendBase更新为100开始，至该段超时重传结束。

**原图未给出RTO及ACK与超时的精确相对时序。** 上述解析采用图示ACK先于超时到达的条件。若seq92的定时器先到期，发送方可能先重传seq92，应另行分析该条件，无法由原图确定数值RTO。

#### 简答6：TCP接收端对不同字节区间的处理

该段范围80–99。下面先假设它处于可接收窗口，并且没有超出99后已缓存的连续数据；否则ACK可能进一步跳过缓存区。

| x范围 | 如何处理 | ACK |
|---|---|---|
| x<80 | 前面x–79有缺口，缓存80–99，暂不按序交付 | x |
| x=80 | 正好按序，接收并交付80–99 | 100 |
| 80<x<100 | 前缀是重复，后缀x–99是新数据；接受后缀 | 100 |
| x≥100 | 80–99全部是已经收到的旧数据，不重复交付 | x |

x>80时应区分部分重叠与全部重复。若题目采用不出现部分重叠段的简化模型，应注明该假设；已缓存的后续连续数据还可能使补齐缺失区间后的ACK进一步增大。

#### 简答7：30KB、MSS1KB、RTT10ms、门限8KB

采用课程的按RTT轮次近似：初始cwnd=1MSS，达到阈值后每轮增加1MSS，立即确认并缓存乱序数据，路径对称，忽略发送时间。**计时从TCP已建立且A在t=0发送第1段开始。** 若从握手开始计时，应另计连接建立时间。

##### (1) 不丢包

| 轮次 | 开始时间ms | cwnd，段 | 本轮实际新发 | 累计新发 |
|---|---|---|---|---|
| 1 | 0 | 1 | 1 | 1 |
| 2 | 10 | 2 | 2–3 | 3 |
| 3 | 20 | 4 | 4–7 | 7 |
| 4 | 30 | 8 | 8–15 | 15 |
| 5 | 40 | 9 | 16–24 | 24 |
| 6 | 50 | 10 | 25–30，共6段 | 30 |

**B完成接收时间55ms；A发第30段时cwnd约10KB。** 第6轮从50ms开始，最后数据再传播半个RTT。最终ACK回A是60ms，与问题的“B完成接收”不同。

这里cwnd按每轮+1的近似；逐ACK用MSS²/cwnd更新时会有小数窗口和舍入差异，不应把轮次表当成所有实现精确到每字节的轨迹。

##### (2) 只有第8段丢，A无快速恢复（Tahoe式）

第4轮在30ms发送段8–15，其中第8段丢失；段9–15在35ms乱序到达并返回相同确认号。重复ACK在40ms到达发送端并触发快速重传。**无快速恢复与无快速重传是不同条件。**

检测丢失前窗口为8KB，因此**ssthresh=4KB，cwnd=1KB**。第5轮仅重传第8段。段9–15虽已在接收端缓存，但尚未得到累计确认，仍计入FlightSize，不能据cwnd=1KB继续注入新数据。

| 轮次 | 时间ms | 操作 / 实际发送 |
|---|---|---|
| 1–4 | 0–30 | 同上；第4轮8–15中8丢 |
| 5 | 40 | 重传8，共1段 |
| 6 | 50 | 累计ACK确认至15；cwnd增长到2，发16–17 |
| 7 | 60 | cwnd4，发18–21 |
| 8 | 70 | cwnd5，发22–26 |
| 9 | 80 | cwnd6，发27–30，共4段 |

**第5轮发送1段，B在85ms完成接收。** 若另外禁止快速重传，则需等待RTO；原题未给出RTO，无法确定唯一完成时间。本解采用具有快速重传机制的Tahoe模型。

##### (3) 第8段丢，A采用Reno快速恢复

假设不使用额外的Limited Transmit，不采用SACK/NewReno等其他恢复策略，接收窗口足够。第4轮窗口8，B对9–15产生7个重复ACK。

40ms第三个重复ACK触发：**ssthresh4KB、cwnd7KB**，重传8。第4、5、6、7个重复ACK依次把cwnd增到8、9、10、11KB。

关键是当时旧的8–15仍有8KB未累计确认。因此：

- cwnd=8时，没有新增空间。
- cwnd=9时，发新段16。
- cwnd=10时，发17。
- cwnd=11时，发18。

**第5轮共发送4段：重传段8，新发段16、17、18。** 可发送的新数据量由临时膨胀后的cwnd与FlightSize之差决定，不能将cwnd=7KB直接解释为可新发7段。

45ms时，B收到重传段8并补齐8–15，随后接收16–18；推进累计确认的ACK在50ms返回。确认缺失区间已恢复的新ACK使发送方**退出快速恢复并将cwnd调整为4KB**，随后进入拥塞避免。

| 轮次 | 时间ms | 实际发送 |
|---|---|---|
| 5 | 40 | 重传8，新发16–18，共4段 |
| 6 | 50 | 发19–22，共4段 |
| 7 | 60 | 发23–27，共5段 |
| 8 | 70 | 发28–30，共3段 |

**B在75ms完成接收；进入快速恢复时cwnd=7KB，退出恢复时cwnd=4KB。** 额外重复ACK可在恢复过程中使cwnd暂时增至11KB，属于窗口膨胀状态。

如果课堂采用“每轮无视已有FlightSize，一律发送整窗口”的更粗略模型，第5轮数目和时间会不同；本题强调只要窗口允许就发，故本解显式扣除在途数据。把假设和时间线写出来，比只背55/85/75三个数更重要。

| DNS查询类型、事务ID、回答和附加记录 | A/CNAME/MX/NS、查询匹配、减少查询次数 |
| DNS用UDP或TCP、TC标志 | 传输选择和截断重试 |
| TCP SYN/SYNACK/ACK、seq/ack | 握手、字节编号、纯ACK不消耗序号 |
| TCP载荷长度、窗口、重传、重复ACK | 接收流控、可靠恢复、拥塞响应 |

Wireshark通常显示**相对序号**，SYN的seq=0和SYNACK的ack=1不表示真实ISN固定为0。HTTP报文可能跨越多个TCP段，应结合重组结果分析。检验和卸载也可能使本机捕获的出站包显示校验异常，该提示不能单独证明链路上发生比特差错。

## 第1–3章考前速查与自测

本文件汇总主要公式、协议机制及自测题。应掌握准确的概念定义、协议执行过程和公式适用条件；需要进一步解释时，可参阅详细讲义及习题解析。

### 1. Web访问与协议协作过程

```text
浏览器访问Web资源
 → DNS解析服务器地址（缓存可减少查询）
 → TCP建立连接（HTTP/1.x或HTTP/2模型）
 → HTTP请求HTML
 → 解析HTML，请求图片等对象
 → TCP按字节编号、确认、重传
 → rwnd约束接收缓存，cwnd约束网络在途数据量
 → IP与链路层完成逐跳交付
```

HTTP/3使用QUIC/UDP；Cookie处理用户状态，缓存处理资源副本，条件GET处理副本是否更新。

### 2. 主要公式与适用条件

| 计算对象 | 公式 | 适用条件 / 注意事项 |
|---|---|---|
| 传输延迟 | L/R | L为bit，R为bit/s |
| 传播延迟 | d/s | 距离与传播速度统一单位 |
| 单分组经过N条等速链路 | NL/R | 存储转发，忽略其他延迟 |
| P个分组经过N条等速链路 | (P+N-1)L/R | 连续流水线传输，考虑链路并行 |
| 流量强度 | ρ=aL/R | ρ接近1排队明显；稳定排队公式要求ρ<1 |
| N个同时到达分组的平均排队 | (N-1)L/(2R) | 初始空队列，不含自身传输时间 |
| 路径吞吐量 | min_i R_i | 无其他流量、无额外限制的理想模型 |
| N条连接共享速率R | 每条约R/N | 还受各端接入速率限制 |
| 单向BDP | R×d_prop | 和R×RTT的反馈窗口口径不同 |
| 停等利用率 | (L/R)/(RTT+L/R) | RTT为来回传播，ACK发送忽略 |
| 窗口W利用率 | min(1,W(L/R)/(RTT+L/R)) | 理想无损 |
| 满载最小窗口 | ceil(1+RTT/(L/R)) | W以分组数表示 |
| GBN序号 | 2^m≥W+1 | 最大W=2^m-1 |
| SR序号 | 2^m≥2W | 等大发送/接收窗口 |
| TCP可新增发送量 | max(0,min(rwnd,cwnd,其他限制)-FlightSize) | MSS规定单段数据量上限 |
| TCP估计RTT | (1-α)旧值+α样本 | α=1/8为课件典型值 |
| TCP偏差 | (1-β)旧偏差+β×绝对误差 | β=1/4，注意更新顺序 |
| RTO | EstimatedRTT+4DevRTT | 超时可指数退避；重传ACK有二义性 |
| 平均Reno速率 | 0.75W/RTT | W为字节；W为段需再乘MSS |
| 丢包率与吞吐量 | 1.22MSS/(RTT√p) | 经典稳态近似 |
| 期望重传次数 | 1/(1-p)^N-1 | 独立链路丢包和独立完整重试 |

单位：1B=8bit；网络速率k/M/G通常按10的幂；题目KB/MSS若只做相同比值，可保持一致，不能把KB和kb混用。

### 3. HTTP耗时计算

HTML+n个小对象，RTT=T，DNS总成本D，初始无连接：

| 模式 | 总时间 |
|---|---|
| 串行非持久 | D+2(n+1)T |
| 持久不流水 | D+(n+2)T |
| 流水线持久，n≥1 | D+3T |
| 非持久、k条并行 | D+2T+2ceil(n/k)T |

对象传输时间不可忽略时，应计入数据量与瓶颈速率。共享速率R的n张Lbit图片，总传输时间为nL/R；并行连接不增加同一瓶颈的总容量。

缓存可直接提供有效对象时，忽略本地传输成本可近似为0。**条件GET即使收到304也需要源服务器往返**，应结合连接状态与串行或流水线调度计算耗时。

### 4. 协议、端口和记录

| 协议 | 服务及传输方式 |
|---|---|
| HTTP | 请求/响应访问资源，基础无状态；传统TCP80 |
| HTTPS | 安全HTTP，常用443；按具体HTTP版本看传输 |
| SMTP | 邮件提交与投递，课程使用TCP25，不提供邮箱读取服务 |
| POP3 | 将邮件下载至本地，TCP110，加密访问常用995 |
| IMAP | 服务器邮箱管理和同步，TCP143，加密访问常用993 |
| DNS | 分布式资源记录数据库，UDP/TCP53 |
| FTP | 控制连接TCP21，数据连接另开；传统主动模式服务端20 |

| RR | 作用 |
|---|---|
| A / AAAA | 名字→IPv4 / IPv6地址 |
| NS | 域→权威服务器名字 |
| CNAME | 别名→规范名字 |
| MX | 邮件域→邮件服务器名字 |
| PTR | 反向查询名字→主机名 |

NS与MX的value通常为主机名，需结合A/AAAA获取地址，响应可附带相关记录。DNS缓存可能省略根查询；查询计数应明确节点范围及是否包含响应。

### 5. TCP序号、确认号与连接管理

- 数据段seq=s、长度l：字节范围s到s+l-1，后续新数据seq=s+l。
- ACK=y表示y之前的数据已连续接收，下一个期望字节序号为y。
- 前序缺失区间未恢复时，累计确认不推进；恢复后可覆盖已缓存的后续连续数据。
- A→B段中的ack确认的是B→A，不是该段自己的数据。
- SYN、FIN各占1序号；普通纯ACK不占。
- 一条TCP连接由源/目的IP、源/目的端口区分，仍是点到点。

| 步骤 | seq | ack | SYN/ACK标志 |
|---|---|---|---|
| A请求 | x | 无效 | 1/0 |
| B回应 | y | x+1 | 1/1 |
| A确认 | x+1 | y+1 | 0/1 |

TCP两个传输方向分别通过FIN与ACK关闭，部分报文段可以合并；主动关闭方通常进入TIME_WAIT。MSS表示单段数据载荷上限，不含TCP/IP首部。

### 6. GBN、SR与TCP可靠传输机制比较

| 协议 | 乱序分组处理 | 确认 | 超时重传 |
|---|---|---|---|
| GBN | 丢弃 | 累计确认至分组n | 重传已发送未确认的分组区间 |
| SR | 缓存 | 单独确认分组n | 仅重传对应超时分组 |
| TCP，课程模型 | 通常缓存 | 累计，ACK y表示下一字节y | 优先重传最早未确认段；另有快速重传 |

GBN的分组序号与TCP的字节序号采用不同确认语义。SR缓存乱序分组，但仍按序向上层交付。

### 7. TCP拥塞窗口更新规则

| 状态 / 事件 | ssthresh | cwnd更新 |
|---|---|---|
| 新连接 | 按题设 | 课程模型从1MSS开始 |
| 慢启动 | 不变 | 每RTT约翻倍，达到门限转拥塞避免 |
| 拥塞避免 | 不变 | 每RTT约+1MSS |
| 超时 | 旧窗口/2 | 1MSS |
| Tahoe三重复ACK | 旧窗口/2 | 1MSS，快速重传但无快速恢复 |
| Reno三重复ACK | 旧窗口/2 | 门限+3MSS，进入快速恢复 |
| Reno恢复中的额外重复ACK | 不变 | 再+1MSS，窗口允许才发新数据 |
| Reno收到更新ACK退出恢复 | 不变 | 回到门限，进入拥塞避免 |

ssthresh根据**丢失检测前的窗口**计算，再更新cwnd。快速重传负责在超时前恢复缺失数据；快速恢复负责调整恢复期间的发送窗口，两者属于不同机制。

若第1轮从t=0开始，共需n轮，路径对称且忽略发送时间，则最后数据在`(n-1)RTT+RTT/2`到达，最终ACK在nRTT返回。

### 8. 易混概念与条件限制

1. 各类延迟的相对大小由具体条件决定；固定路径上的延迟抖动主要来自排队。
2. ρ<1仍可能出现瞬时排队；ρ≥1时不适用稳定平均延迟公式。
3. TCP和UDP都不保证最低带宽与最大时延。
4. UDP可做可靠应用，TCP基础服务不自动加密。
5. HTTP无状态不等于网站无状态；Cookie不等于缓存。
6. Date表示响应生成时间，Last-Modified表示对象修改时间；304验证仍涉及网络往返。
7. P2P交互可区分客户与服务器角色；tracker用于资源发现，文件不必经tracker转发。
8. SMTP负责投递，邮箱访问可用POP3/IMAP/HTTP。
9. 本地DNS不属根/TLD/权威层次；512B是传统DNS模型。
10. 同一服务器端口可对应多条独立TCP连接，每条连接仍为点到点。
11. TCP确认不意味着应用已经读取数据，可用接收窗口仍由缓存占用决定。
12. ACK丢失可能被后续累计ACK覆盖，不必一定重传。
13. 首个推进SendBase的ACK不是重复ACK。
14. seq较小的段也可能部分重叠并携带新字节。
15. Reno进入快速恢复的cwnd与退出恢复后的cwnd应分别分析。
16. 新数据发送量应扣除FlightSize；重传不计入新的文件数据量。
17. MSS4KB允许发2KB小段。
18. 无快速恢复不意味着禁用快速重传；仅采用超时恢复且未给RTO时，无法确定数值完成时间。

### 9. 20道闭卷自测

建议先独立完成各题，写出简要依据或计算步骤，再核对答案。

1. 分组交换为什么适合突发流量？
2. 1500B通过12Mbps空链路，传输时间是多少？
3. 1000km光纤，传播速度2×10^8m/s，传播时间是多少？
4. 3跳、100个等长包、每个分组发送2ms，总时间多少？
5. 平均每秒100包，每个分组10000bit，链路2Mbps，ρ是多少？
6. 根、本地和权威DNS服务器中，哪一类保存机构的资源记录？哪一类负责代理用户查询？
7. 网页包含HTML及8个小对象，采用6条并行非持久连接且忽略DNS和传输时间，总耗时为多少RTT？
8. 说明缓存对象未修改时，条件GET仍需要远端往返的原因。
9. 用户从邮箱读取邮件为什么不用SMTP？
10. P2P对等方在下载数据的同时，能否向其他对等方上传数据？
11. UDP首部长度是多少？UDP长度字段是否包含IP首部？
12. ACK丢失引起重传时，协议通过何种机制避免重复交付？
13. 3bit序号，GBN/SR最大等大窗口各多少？
14. TCP接收端期待序号100，先收到seq=150、长度50B的报文段，确认号是多少？
15. 随后收到seq=100、长度50B的报文段，且150–199已经缓存，确认号是多少？
16. seq=100的段携带40B数据，下一新段的序号是多少？普通纯ACK是否消耗序号？
17. cwnd=32KB、rwnd=40KB、已发送未确认30KB，允许新增发送的数据量是多少？
18. Reno丢失检测前窗口为12MSS，收到3个重复ACK后，ssthresh及进入、退出快速恢复时的cwnd各是多少？
19. 各轮窗口为1、2、4、8、9、10，发送30个段时第30段属于哪一轮？RTT=10ms时最后数据何时到达？
20. 说明流量控制与拥塞控制的控制对象。

#### 自测答案

1. 统计复用按需共享容量，使空闲用户的资源可供活跃用户使用。
2. 1ms。3. 5ms。4. 204ms。5. 0.5。
6. 权威DNS保存所负责区域的资源记录，本地DNS代理查询并缓存结果。
7. 6RTT。8. 条件GET验证仍需回源往返。
9. SMTP提供邮件提交和投递，不提供邮箱读取。10. 可以，对等方能够同时承担两种角色。
11. 8B；长度含UDP首部和载荷，不含IP头。
12. 数据序号、接收端去重。13. GBN7，SR4。
14. 100。15. 200。16. 140；普通纯ACK不加1。
17. 2KB。18. 门限6，刚进入9，退出后6MSS。
19. 第6轮；从第1轮t=0起，55ms，最终ACK60ms。
20. 流量控制约束接收缓存及读取能力，拥塞控制约束网络链路和路由器负载。
